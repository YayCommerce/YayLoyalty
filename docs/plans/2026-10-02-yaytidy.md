# yaytidy Implementation Plan

> **For agentic workers:** execute tasks in order, one at a time. Steps use `- [ ]` for tracking. Read the spec linked below before starting; the plan argues from it.

**Status:** done 2026-10-02
**Goal:** add the `/yaytidy` skill. Before a PR, it runs the built-in `/simplify` behind a guard, then reports duplicated facts, drifted or stale owner markers and redundant code. It fixes only the findings the developer picks.
**Spec:** [docs/specs/2026-10-02-yaytidy-design.md](../specs/2026-10-02-yaytidy-design.md)
**Architecture:** one skill directory: `SKILL.md` holds the modes, the PR-base rule and the run, and `references/finding-kinds.md` holds what to look for and how to report it. Owners come from markers in code and from the repo's rules, never from a table (spec, Alternatives). The skill is prose, not code, so each task is verified by the harness checks plus a scripted run on a throwaway scratch branch.
**Touches:** `.claude/skills/yaytidy/` (new). `docs/decisions/` (one new record, plus one Status line in the shared skills record). `docs/plans/2026-10-01-harness-renewal.md` (§4, §6, P11, V8). The PR-base rule is **shared** wording: the yaycook plan copies it into yaycook and yayreview word for word, so treat Task 1's `## PR base` section as an interface.
**Shipping:** yaytidy ships in its own PR, before yaycook (user's choice, 2026-10-02). So this PR writes the shared decision record for both skills, and the yaycook plan only links to it.

## Global constraints

- Skill `name` is `yaytidy`, equal to its directory, matching `^[a-z0-9-]+$` (C12).
- `description`: one line, ≤ 500 characters (C12), keeps a "Do not use" clause that rules out bug hunting, lint, and naming or style requests.
- Frontmatter has `argument-hint: "[base <ref> | commit <sha> | <path>…]"`, quoted exactly like that.
- Purpose and Update when go in YAML comments in the frontmatter, as in `.claude/skills/yayreview/SKILL.md`. Update when names yaycook and yayreview, which share the PR-base rule.
- Repo-neutral: the base, the commands, the failing checks and the rules come from `CLAUDE.md` and the docs it links. No machine paths, tool versions, doc section numbers, line-number citations, `dev/edd`, `composer` or YayLoyalty paths in the skill's files.
- Reference files are linked with markdown links, never as backticked paths. C16 resolves backticked paths from the repo root. A bare backticked `refs/heads/` also trips C16, so keep it inside the full backticked command.
- None of the removed checker's names (C2's list) appears anywhere. No hyphenated or spaced "source of truth" followed by "check" appears either, headings included.
- Evals use skill-creator's `evals/evals.json` format (`skill_name`, `evals[]` of `id`, `prompt`, `expected_output`, `files: []`). Their prompts are repo-neutral, and they never apply patches.
- Depends on the built-in `simplify` skill (Claude Code ≥ 2.1.283).
- `CLAUDE.md` § Git: branch from the base as `<name>/<type>/<topic>`, Conventional Commits with the Co-Authored-By trailer, stage by name, commit only when asked. Never edit generated directories.
- Scratch branches used for verification are deleted afterwards, and nothing from them is pushed.

## Decisions this plan makes (the spec leaves them open)

- **"No longer exists" means the upstream is gone.** A stack parent counts as probably squash-merged when `git for-each-ref --format='%(upstream:track)'` prints `[gone]`. A branch that was never pushed has no upstream, so it is a live parent. The skill doesn't fetch; it uses the remote-tracking refs it has.
- **Parents at HEAD are left out.** That covers any branch with 0 commits in `git rev-list --count <parent>..HEAD`, as well as the current branch.
- **Four slots in the base question.** AskUserQuestion takes at most 4 options: the nearest live parent (Recommended), the `CLAUDE.md` base, the next parent, then Other. Gone parents rank after every live parent, so one appears only when too few live parents fill the slots. Its description then says "probably squash-merged and deleted".
- **Surviving lines (commit mode).** A line the commit changed that still exists is a line that `git blame --line-porcelain HEAD -- <file>` attributes to `<sha>`. The rewritten count is the lines the commit added, from `git diff --numstat <parent> <sha>`, minus the surviving lines. `<parent>` is `<sha>^1`, or the empty tree `git hash-object -t tree /dev/null` for a root commit. A commit that only deleted lines has nothing left to check.
- **Removed or renamed symbols (branch mode).** A symbol counts as removed or renamed when it is declared on a `-` line of `git diff <base>...HEAD` and `git grep -nw <name>` finds no declaration of it at HEAD. Every comment that names it, in any tracked file, is a stale-marker candidate.
- **The guard's question.** Uncommitted in-scope files get "Commit them yourself, then continue" (Recommended), "Continue without committing" (the report warns that /simplify's edits mix with theirs) or "Stop". yaytidy never commits them.
- **Over 20 files in path mode.** The question offers "Run /simplify on all N files", "Skip /simplify, own pass only" and "Stop to narrow the paths".
- **Finding IDs** are plain numbers, `1`…`n`, which the developer types under Other.
- **Ranking when there are more than 20 findings**, by kind: drifted mirror, owner dispute, unowned copy, copy, stale marker, duplicated logic, redundant code. Within each kind, `contract` findings come first.
- **"No new failures".** Each narrowed check runs once before the fixes and once after. A failure is new when the run before the fixes didn't show it. A test run that executed no tests (for example "No tests executed!", or "No test files found") counts as failed both times.

## Review focus

- A stacked branch with a parent that is nearer than every live parent but whose upstream is `[gone]`: it must rank after the live parents, and live parents (pushed or never pushed) must carry no squash-merged note (Task 1, Step 5, case C).
- `/yaytidy base <bad ref>`: refused before anything runs, with `git status --porcelain` unchanged (Task 1, Step 5, case B).
- A marker outside the diff that names a symbol the diff renamed: reported as a stale marker (Task 1, Step 5, case A).
- A `contract` finding under "fix all": it is skipped unless it is picked by its ID (Task 2, Step 3, case E).
- Negated or vague wording, such as "nothing to keep in sync" or "mirrored server-side": never read as an owner (Task 2, Step 3, case F).
- A quoted glob, and a path that matches no tracked file: the glob expands, and the unmatched path is refused with its reason (Task 2, Step 3, case G).
- A commit that only deleted lines, or whose lines were all rewritten later: "nothing left to check" (Task 3, Step 3, case J).
- A commit outside HEAD's history: refused. A commit already in the base: the scope line says so (Task 3, Step 3, case I).
